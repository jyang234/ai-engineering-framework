# Acme Integration Demo — Detailed Instructions

This document explains how the demo works, what it tests, and the nuances you should keep in mind when running it.

## Purpose

This demo serves two purposes:

1. **Showcase** — Demonstrates EDI's full lifecycle to new users or evaluators in a controlled, repeatable scenario.
2. **Shakedown test** — Exercises every major EDI feature against a realistic (but fake) project. Failures are expected on first runs and are valuable diagnostic data.

The demo is **not** an automated test suite. Several steps require human interaction with an LLM. Non-deterministic outputs mean you should focus on *whether the right information surfaced*, not on exact output matching.

## Architecture of the Demo

```
demo/acme-integration/
├── setup.sh          # Idempotent — safe to re-run
├── teardown.sh       # Destructive — removes all runtime state
├── verify.sh         # Stateless checks + LLM judge + result logging
├── .edi/profile.md   # Pre-written; setup.sh won't overwrite it
├── docs/             # Static project artifacts (PRD, ADRs, data contract)
├── src/main.go       # Skeleton with TODOs matching PRD user stories
├── checkpoints/      # JSON specs defining what each step should produce
└── .demo/            # Runtime only (gitignored by setup.sh)
    ├── results.json  # Append-only structured deviation log
    └── RESULTS.md    # Human-readable summary (generated by verify.sh summary)
```

### Isolation Model

- **Git**: `setup.sh` creates a fresh git repo *inside* `demo/acme-integration/`. This is a nested repo — it won't interfere with the parent AEF repo.
- **RECALL**: With `backend: codex` (the demo default), both `edi recall add` CLI and the MCP server write to the same Codex database (`~/.edi/codex.db`). The demo seeds 3 items with "acme" tags. This means CLI seeding and in-session RECALL queries hit the same data.
- **EDI config**: `edi init --force` creates `.edi/config.yaml` in the demo dir. It also overwrites `profile.md`, so `setup.sh` saves and restores the custom profile around the init call.
- **Global `~/.edi/`**: Read for agents, commands, config. Never written by the demo.

## Step-by-Step Nuances

### Step 1: Setup (`./setup.sh`)

**What happens:**
- Creates a git repo with all demo files as the initial commit
- Runs `edi init --force` to generate `.edi/config.yaml`
- Seeds 3 RECALL items via `edi recall add`

**Nuances:**
- If you've already run setup before, it's idempotent — won't re-init git or re-create config.
- RECALL seeding uses `--if-not-exists` and is idempotent — running setup twice won't create duplicates.
- If `edi recall add` fails (e.g., RECALL not configured), setup continues with a warning. You can seed manually later.

### Step 2: Explore RECALL

**What to watch for:**
- `edi recall search "auth"` should return the ADR-001 item and possibly the kickoff meeting notes (which mention OAuth).
- If RECALL returns 0 results, seeding in step 1 may have failed. Check that your RECALL backend is configured (`edi doctor`).
- FTS5 ranking may vary — the meeting notes might rank higher than the ADR if the query terms appear more frequently.

**Common issue:** If using the Codex backend, the recall-mcp binary must be built and installed for in-session RECALL. The `edi recall` CLI uses the Codex database directly (no MCP binary needed). Use `edi doctor` to verify the full setup.

### Step 3: Architect Mode

**What you're testing:**
- Does `/plan` switch EDI to architect mode?
- Does the LLM reference RECALL knowledge (ADR-001, ADR-002) when designing the integration?
- The briefing injected at session start should include the profile context, which mentions OAuth and JSON decisions.

**Nuances:**
- The LLM may or may not explicitly call `recall_search`. Even if it doesn't, the briefing already contains project context from the profile.
- The `llm_judge` verification is semi-automated: Claude evaluates whether the plan referenced OAuth/ADR-001, then asks you to confirm. LLM judge costs ~$0.01-0.05 per check.
- If the LLM produces a plan that's technically correct but doesn't mention the ADRs, that's a **capability gap** signal — the RECALL retrieval or briefing didn't surface context effectively.

**Recovery:** If the session crashes or you exit early, just start a new `edi` session and try again. No state is lost.

### Step 4: Implement

**What you're testing:**
- Does `/build` switch to coder mode?
- Can the LLM implement against the data contract (`docs/data-contract-v1.yaml`)?
- Does it create commits?

**Nuances:**
- The LLM will modify `src/main.go` and likely create new files. The verification only checks that `src/main.go` was modified and at least 1 commit was made.
- You may need to explicitly ask the LLM to commit. EDI doesn't auto-commit.
- If the LLM creates a `go.mod` file, that's fine — the skeleton doesn't include one.
- The TODOs in `src/main.go` reference user story IDs (US-001, US-002, etc.) to guide the LLM.

**Recovery:** If implementation goes wrong, `git reset --hard HEAD` and try again.

### Step 5: Review

**What you're testing:**
- Does `/review` switch to reviewer mode?
- Does the review reference security concerns from RECALL (e.g., OAuth token handling)?
- Is the review constructive and actionable?

**Nuances:**
- The review depends on what was implemented in step 4. If step 4 was skipped or minimal, the review will be thin.
- The `llm_judge` check here is the fuzziest — "did the review mention security" is subjective. Your human confirmation is the final authority.

### Step 6: Ralph Loop

**What you're testing:**
- Does `edi ralph --prd docs/PRD.json` work end-to-end?
- Does Ralph iterate through user stories, implement them, and mark them as passing?
- Does it produce git commits?

**Nuances:**
- This is the highest-signal step. Ralph invokes Claude Code in a loop, and each iteration is a fresh context window. If this works, most of EDI's machinery is functioning.
- Ralph reads `PRD.json`, picks the next incomplete task, implements it, runs verification, and marks it as done. Each iteration creates a commit.
- The PRD has 4 user stories. Expect Ralph to complete at least 2 for the verification to pass.
- **This step can take a while** — each iteration is a full Claude Code session. Budget for ~2-5 minutes per user story.
- If Ralph gets stuck (3 consecutive failures on the same task), it will auto-escalate and move to the next task.
- Ralph creates a `.ralph/` working directory. This is gitignored by the `edi ralph` command.

**Common issues:**
- Ralph may fail if Go isn't installed (it needs to compile/test the code)
- The PRD `depends_on` field controls task ordering — US-002 won't start until US-001 passes
- If Ralph marks a task as passing but the code doesn't actually work, that's a **verification gap** signal

**Recovery:** If Ralph exits mid-loop, just re-run `edi ralph --prd docs/PRD.json`. It picks up where it left off by reading PRD.json task states.

### Step 7: Session End

**What you're testing:**
- Does `/end` trigger the session summary flow?
- Are you prompted to save knowledge items to RECALL?
- Do saved items actually appear in subsequent RECALL searches?

**Nuances:**
- The `/end` command generates a session summary and identifies "capture candidates" — decisions, patterns, or failures worth saving.
- You need to manually confirm which items to save. Save at least one "decision" type item for the verification to pass.
- The verification checks that a RECALL item with type "decision" exists in project scope. If you saved to global scope, the check may fail depending on your RECALL setup.

### Step 8: Results Summary

Running `./verify.sh summary` generates `.demo/RESULTS.md` from all accumulated results in `.demo/results.json`.

**Reading the results:**
- **pass** — Deterministic check succeeded
- **llm_pass** — LLM judge ruled pass, human confirmed
- **overridden_pass** — LLM judge ruled fail, human overrode to pass
- **overridden_fail** — LLM judge ruled pass, human overrode to fail
- **fail** — Deterministic check failed
- **llm_fail** — LLM judge ruled fail, human confirmed
- **skip** — Check couldn't run (e.g., claude CLI not available)

**Interpreting failures:**
- **Demo failures** (setup/tooling broke): File missing, git not initialized, jq not installed. These are bugs in the demo itself.
- **Capability gaps** (EDI feature didn't deliver): RECALL didn't surface relevant context, agent mode switch didn't change behavior, Ralph couldn't complete a task. These are prioritized improvement items for EDI.

## Deviation Log Format

`results.json` is an append-only JSON array. Each entry:

```json
{
  "step": "02-recall-seed",
  "check": "recall_contains:auth",
  "expected": ">= 1 results",
  "actual": "2 results",
  "status": "pass",
  "notes": "",
  "timestamp": "2026-01-31T12:00:00Z"
}
```

For LLM judge checks, the `actual` field contains the LLM's reasoning. The deviation log becomes a bug backlog: each failure maps to a concrete fix in either the demo or EDI itself.

## LLM-as-Judge Cost

LLM judge checks pipe a short prompt to `claude -p`. Each invocation costs ~$0.01-0.05 depending on context length. The demo has 4 LLM judge checks (steps 03 and 05), so a full run costs ~$0.04-0.20 in LLM judge fees.

## Running on a Fresh Machine

This is the most valuable test. It will surface:

- Missing dependencies (Go, jq, claude CLI)
- PATH issues (edi not found)
- RECALL configuration problems
- Permission issues

Run `edi doctor` first to diagnose common issues.

## Tips

- Run `edi doctor` before starting to verify your installation
- Use `./verify.sh` without arguments to see available steps
- Steps can be re-run — results accumulate in the log
- `./teardown.sh && ./setup.sh` for a clean restart
- The demo uses RECALL backend `codex` — CLI and MCP server share the same database
- If you're just testing Ralph, you can skip steps 3-5 and go straight to step 6
